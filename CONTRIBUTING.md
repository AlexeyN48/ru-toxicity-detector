# Правила работы с репозиторием

## Подготовка окружения

Нужен Python 3.11+. Один раз после клонения репозитория:

```bash
python -m venv .venv
# Windows:      .venv\Scripts\activate
# Linux/macOS:  source .venv/bin/activate
pip install -e ".[dev]"
pre-commit install
```

После `pre-commit install` перед каждым коммитом автоматически запускаются проверки:
линтер и форматтер `ruff`, удаление лишних пробелов, проверка YAML/TOML, запрет файлов
больше 1 МБ (данные и веса моделей не коммитим) и поиск приватных ключей. Если хук что-то
исправил сам, коммит прервётся: проверьте изменения, сделайте `git add` и закоммитьте снова.

Запустить проверки вручную:

```bash
pre-commit run --all-files   # все хуки на всех файлах
ruff check . --fix           # только линтер
ruff format .                # только форматирование
```

Те же проверки запускаются в GitHub Actions на каждый push в `main` и на каждый Pull Request.
PR с красным CI не мерджим.

## Ветки (GitHub flow)

- `main` — всегда рабочая ветка. Напрямую в неё не пушим, изменения попадают только через Pull Request.
- Новая функциональность — `feature/<название_фичи>`, например `feature/add-models`.
- Исправление бага — `fix/<название_фикса_или_бага>`, например `fix/endpoint-extract-text`.
- Названия веток пишем на английском, слова разделяем дефисом.

Одна ветка — одна задача — один Pull Request.

## Коммиты

- Пишем на английском.
- Добавление функциональности начинается с `feature:`, исправление — с `fix:`.
- Документация и настройки тоже идут через `feature:`, если это не исправление.

```
feature: add README.MD
fix: fix docker file
```

## Pull Request

1. Описание короткое и ёмкое, на английском. Заполняем шаблон, который подставляется автоматически.
2. Обязательно назначаем ревьюера.
3. После создания PR тегаем ревьюера в чате команды и даём ссылку на PR.

## Код-ревью

Код-ревью — важная часть сдачи проекта, поэтому проводим его по каждому PR.

- Оставили комментарий — тегаем автора PR.
- Замечания к уже существующему коду, который переносим по ролям, пишем в текущих PR.
- Принимаем PR — мерджим ветку и оставляем в комментариях доброе слово.
- Если ревьюер предлагает сделать иначе, автор аргументированно отвечает, почему выбрал
  именно такое решение. Когда стороны договорились, ревьюер закрывает тред.

## Секреты

Токены и пароли (например, токен Telegram-бота) не коммитим. Они хранятся только в `.env`
(файл в `.gitignore`) и в GitHub Secrets.
